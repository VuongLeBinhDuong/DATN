This chapter presents the system design, implementation details, and evaluation results of the smart medical QA and consultation platform. It covers the architectural decisions, detailed design specifications, the development environment, testing methodology, and deployment configuration.

\section{Architecture design}
\label{section:4.1}

\subsection{Software architecture selection}
\label{subsection:4.1.1}

The system adopts a Clean Layered Architecture pattern, which strictly separates concerns across four distinct horizontal layers. This architecture was selected over alternative patterns (e.g., monolithic MVC or microservices) because it provides a clear dependency rule — each inner layer does not know about outer layers — which is essential when integrating multiple heterogeneous backends such as a graph database, a local LLM runtime, and a document parser.

The four layers are defined as follows. First, the Presentation Layer includes the \texttt{api/} and \texttt{web\_ui/} modules, which are responsible for HTTP routing, request validation via Pydantic, streamed NDJSON responses, and serving the browser-based user interface. Second, the Business Logic Layer includes the \texttt{services/}, \texttt{agent/}, and \texttt{medical\_records/} modules, which orchestrate the ReAct agent loop, medical file analysis pipeline, and medication reminder management. Third, the Data Access Layer includes the \texttt{repositories/} and \texttt{llm\_pipeline/} modules, which abstract all data queries behind repository interfaces and manage Cypher queries to Neo4j and prompt formatting to Ollama. Fourth, the Infrastructure Layer includes the \texttt{core/} and \texttt{config/} modules, which manage settings injection, connection pooling, and database container management.

This design decoupling allows the system to remain flexible and deployable across varying computing resource environments. Specifically, the \texttt{OllamaBackend} connects to a locally hosted Ollama server (defaulting to \texttt{http://localhost:11434}), ensuring compliance with data privacy regulations and eliminating network transaction costs by running LLM inference locally. Alternatively, the \texttt{OpenRouterBackend} connects to the cloud-based OpenRouter API, providing compatibility with proprietary or large-scale language models (such as GPT-4 or Claude) when high reasoning capacity is needed or local GPU resources are constrained.

At runtime, the selection is managed dynamically by the backend setting factory \nolinkurl{get\_llm\_backend()}. If the environment parameter \texttt{LLM\_BACKEND} is set to \texttt{"openrouter"} and a valid \texttt{OPENROUTER\_API\_KEY} is configured, the system routes all agent consultation requests to the OpenRouter gateway. To ensure system resilience, the factory implements an automatic fallback mechanism: if OpenRouter initialization fails due to missing keys or configuration issues, the engine logs a warning and automatically falls back to the local \texttt{OllamaBackend} runtime, preventing application downtime.

\section{Detailed design}

\subsection{User interface design}
\label{subsection:4.2.1}

The Web UI targets standard desktop browsers (Chrome, Firefox, Edge) at a minimum resolution of $1280 \times 720$ pixels. The design follows a dark-themed, high-contrast palette with HSL-based color tokens, reducing eye strain during extended clinical readings.

Key interface conventions are defined to ensure a consistent user experience. The Agent Chat Panel displays the user's message on the right and the agent's streamed response on the left, with active \textit{Thinking...} spinners during tool execution and collapsible source-citation blocks below each answer. The Document Upload Panel consists of an upload drop-zone with real-time progress feedback, where a two-column layout renders the raw extracted text on the left and the benchmark table (with color-coded indicators for normal, below, or above reference bounds) on the right. The Pill Cards are inline visual cards rendered inside agent responses whenever a drug name is identified, showing the pill's image, name, and dosage form. The Reminder Calendar presents a weekly schedule grid where each medication intake slot is shown as a colored time block with a notification alarm badge.

\subsection{API Endpoints and JSON Contract Specifications}
\label{subsection:4.2.4}

To standardise communication between the Vanilla Web UI and the FastAPI gateway, all endpoints consume and yield strictly validated JSON payloads. This subsection details the contract schemas for the three primary functional pipelines.

\paragraph{1. Streamed Agent Consultation Endpoint (\texttt{POST /api/agent-query/stream})}
This route processes natural language patient queries and returns a stream of Server-Sent Events (SSE) representing intermediate thoughts, tool execution observations, and the final clinical answer.

\begin{lstlisting}[basicstyle=\footnotesize\ttfamily,breaklines=true,columns=fullflexible]
// Request JSON Payload
{
  "query": "Does drug Paracetamol interact with Warfarin?"
}

// Response NDJSON Stream Example Chunks
{"type": "thought", "content": "The user is asking about an interaction between Paracetamol and Warfarin. I should query the custom Neo4j KG."}
{"type": "action", "tool": "graphrag_query", "tool_input": "Paracetamol, Warfarin"}
{"type": "observation", "content": "Found relationship: Paracetamol INTERACTS_WITH Warfarin (Confidence: 0.85, evidence: Concurrent use may increase bleeding risk)."}
{"type": "final_answer", "content": "Yes, concurrent use of Paracetamol and Warfarin may increase bleeding risk. Please consult your physician."}
\end{lstlisting}

\paragraph{2. Medical Record Analyzer Endpoint (\texttt{POST /api/medical-record/analyze})}
This endpoint accepts multipart form file uploads (.xlsx, .pdf), parses the physiological test indicators, and returns a structured comparison model along with RAG-grounded clinician advice.

\subsection{Core Procedural Algorithms}
\label{subsection:4.2.5}

The runtime execution logic of the clinical agent is governed by two primary algorithms. Algorithm 1 outlines the robust local ReAct agent loop equipped with format healing and iteration limits. Algorithm 2 details the dual-stage Graph-First retrieval logic that isolates verified graph paths before querying.

\begin{algorithm}[H]
\SetAlgoLined
\KwIn{Patient query $q$, system instructions $S$, toolset $T$, maximum iterations $I_{max} = 3$}
\KwOut{Streamed answer chunks, final grounded clinical report}
Initialize empty chat history Scratchpad $C \leftarrow \emptyset$\;
Start NDJSON stream response\;
\For{iteration $i = 1$ \text{to} $I_{max}$}{
    Send prompt $(S + q + C)$ to local LLM backend\;
    Receive raw string output $O_i$\;
    Try to parse $O_i$ for JSON schema matching $\{\text{Thought}, \text{Action}, \text{Action Input}\}$\;
    \If{parsing fails (ParsingError)}{
        Apply Regex-based JSON healer to repair quotes/brackets\;
        \If{repair fails}{
            Append synthetic error message to $C$ as system observation\;
            Continue to next iteration (Self-Correction)\;
        }
    }
    Extract action $a \leftarrow O_i[\text{Action}]$, parameter $p \leftarrow O_i[\text{Action Input}]$\;
    \If{$a = \text{"Final Answer"}$}{
        Stream final response text and citations\;
        Terminate loop and return\;
    }
    \If{active action $(a, p)$ matches previous iteration}{
        Trigger Loop-Guard: Terminate execution, force final synthesis over current context $C$, and return\;
    }
    Execute tool $t \in T$ using parameter $p$\;
    Receive database/file result observation $o \leftarrow \text{Execute}(t, p)$\;
    Format observation $o$ and append to $C \leftarrow C \cup \{\text{Thought } t_i, \text{Action } a_i, \text{Observation } o\}$\;
    Stream status update block to client UI\;
}
Trigger forced finalization\;
Stream final response compiled from available Scratchpad $C$\;
\caption{Local ReAct reasoning-acting execution loop with safeguards}
\label{alg:react_loop}
\end{algorithm}

\vspace{0.4cm}

\begin{algorithm}[H]
\SetAlgoLined
\KwIn{User query $q$, Neo4j graph database instance $DB$, max hops $H_{max} = 2$}
\KwOut{Retrieved clinical evidence chunks and paths}
Extract clinical entity mentions using lightweight 1.5B local model: $E_{mentions} \leftarrow f_{NER}(q)$\;
Initialize seed node list $V_{seed} \leftarrow \emptyset$\;
\ForEach{mention $m \in E_{mentions}$}{
    Query Neo4j fulltext index matching $m$ against aliases or canonical names\;
    \If{exact or high-confidence match found}{
        Add resolved node ID to $V_{seed}$\;
    }
}
\If{$|V_{seed}| \ge 2$}{
    Execute Cypher path query matching paths linking any two nodes in $V_{seed}$ with length $\le H_{max}$\;
    Extract connecting edges $R_{paths}$\;
    \If{$R_{paths}$ is not empty}{
        Gather unique \texttt{evidence\_chunk\_id} attributes from matched edges\;
        Load evidence text paragraphs from corresponding database `Chunk` nodes\;
        Return formatted subgraphs and chunk contents\;
    }
}
Execute k-Hop neighborhood expansion around seed nodes $V_{seed}$ up to $H_{max}$ hops\;
Retrieve neighboring entity nodes and associated evidence chunks\;
Return k-hop context\;
\caption{Graph-First hybrid context retrieval logic}
\label{alg:graph_retrieval}
\end{algorithm}

\subsection{Performance Latency Optimizations}
\label{subsection:4.3.4}

By splitting the LLM workloads between a main 3B reasoning model and a parallel 1.5B classification model, the system latency was optimized. Specifically, for Query Classification (Intent Router), the latency was reduced from $2.4\text{s}$ (with a 3B model) to $1.1\text{s}$ (Qwen-2.5-1.5B), achieving a $54\%$ speedup. Furthermore, for Clinical Entity Extraction, the retrieval path is designed to identify structured clinical entities before graph querying, reducing irrelevant context before prompt construction.


Beyond raw latency, the implementation focuses on clinical usability. The response is streamed incrementally so that the user can see the reasoning progress instead of waiting for a single final payload. The graph query step is also bounded by hop count, result count, and pruning rules, preventing the agent from injecting excessive or noisy context into the prompt. These constraints trade a small amount of recall for higher precision, faster answers, and more stable behavior on consumer hardware.

\subsection{Language Model Implementations and Backend Configurations}
The system's reasoning pipeline is designed to be model-agnostic, supporting both local and cloud-based inference endpoints. In the local offline configuration, the reasoning agent is hosted natively using the 3-billion parameter \texttt{llama3.2:3b} model running the multi-turn ReAct reasoning loop, while the intent routing and NER tasks are managed by a parallel instance of the 1.5-billion parameter \texttt{qwen2.5:1.5b-instruct} model to ensure low latency. In the cloud fallback configuration, the system connects via API to OpenRouter, querying high-parameter models to establish a high-accuracy baseline during clinical testing and staging.

\subsection{Evaluation Limitations}
The evaluation results reveal useful engineering signals, but they should not be interpreted as final clinical validation. First, the retrieval benchmark is small, meaning Precision@K and Recall@K are sensitive to a few difficult queries and entity-normalization quality. Second, BLEU-4 and ROUGE-L metrics are conservative for Vietnamese medical QA because correct answers can be paraphrased with different wording. Third, standard cloud-based RAGAS evaluation tools were bypassed due to formatting mismatch and local resource limits, focusing instead on local semantic (SBERT) and clinical safety benchmarks. Finally, none of these automatic metrics replaces human clinical review; they should be used as regression signals during system development.

\subsection{Complementary Evaluation Scripts}
The project also keeps complementary scripts: \texttt{eval/eval\_local.py} for semantic similarity, ROUGE-L, BLEU-4, ReAct step count, parse status, and loop-guard status; \texttt{eval/eval\_comparison.py} for Pure LLM vs GraphRAG answer comparison; \texttt{eval/eval\_custom\_kg.py} for custom KG retrieval quality; \texttt{eval/retrieval\_evaluator.py} for Precision@K, Recall@K, F1, MRR, and NDCG; and script-level evaluators such as \texttt{scripts/eval\_graph\_rag.py} and \texttt{scripts/eval\_retrieval\_quality.py}.

Overall, the testing strategy validates both software correctness and clinical-answer behavior. The comparative suite is the most important addition because it evaluates GraphRAG against direct LLM generation using factual, safety, graph-retrieval, latency, and judge-based criteria.


\section{Deployment}
\label{section:4.5}

The system is deployed locally using a hybrid approach: the Neo4j database is containerized via Docker for data persistence and volume isolation, while the Ollama LLM runtime and FastAPI backend run natively on the host operating system to optimize VRAM utilization and reduce latency on local hardware. To enable clinical testing by remote reviewers, the local server is exposed securely using an HTTPS tunnel. The deployment of each component is structured as follows. For the graph database, Neo4j is run as a standalone Docker container, exposing the Bolt protocol endpoint on port \texttt{7687} and the interactive database browser on port \texttt{7474}, while database files and logs are persisted to Docker volumes. The local LLM runtime (Ollama) is run natively on the host system to enable direct access to system GPU resources and exposes the offline inference API on port \texttt{11434}. The FastAPI application server is run natively within a Python virtual environment (\texttt{venv}), connecting to Neo4j and Ollama via localhost endpoints on port \texttt{8000}. Finally, secure external tunneling is achieved by deploying \texttt{ngrok} as a secure tunneling agent, mapping the local FastAPI server to a public HTTPS URL to allow external clinical experts and mobile testing clients to interact with the consultation portal without modifying local router configurations.

The main setup and execution commands are:

\begin{verbatim}
# 1. Start Neo4j in a Docker container using docker-compose
docker-compose up -d

# 2. Run Ollama natively and pull the local LLM models
ollama serve
ollama pull llama3.2:3b
ollama pull qwen2.5:1.5b-instruct

# 3. Start the FastAPI backend application
python -m uvicorn api.main:app --host 127.0.0.1 --port 8000 --reload

# 4. (Optional) Expose local FastAPI backend server securely using ngrok
ngrok config add-authtoken [YOUR_NGROK_AUTH_TOKEN]
ngrok http 8000
\end{verbatim}

After starting the Neo4j container, the database graph browser is available at \nolinkurl{http://localhost:7474}, and the backend communicates using the Bolt protocol at \nolinkurl{bolt://localhost:7687}. If Ollama is running natively, the backend interacts with the model runner at \nolinkurl{http://localhost:11434}. The API service then serves the user interface and exposes REST endpoints. When ngrok is active, it generates a public, secure domain (e.g., \nolinkurl{https://[subdomain].ngrok-free.app}) that routes incoming external traffic through the ngrok tunnel directly to the local FastAPI backend, enabling mobile consultations while keeping all healthcare processing and knowledge base resources strictly private on the host machine.
